# Computer use

A port of Tomo's computer use. The model looks at the screen, reads and drives the user's apps, finds files, and in Show-me mode spotlights each control and waits for the user to do it. `index.ts` is the only entry point.

## Wiring it in

`src/main/index.ts` builds the layer, and `src/main/services/Chat.ts` uses it:

```ts
ComputerUse.layer({
  platform: supported ? makePlatform({ track: trackChild }) : null, // track: quitting ends the host
  overlay: makeElectronOverlay({ refocus }), // never shown with CHAT_V2_HEADLESS=1; refocus: platform.remember() then restoreFocus()
  remember: async (fact, ctx) => void db.changeMemory({ add: [fact], update: [], remove: [] }, { kind: 'learned', sessionId: ctx.sessionId })
})
```

- **A reply**: `computer.module(ctx, { mode, setMode, stop })` joins the reply's tool sets when its chat has computer use on. `mode` is read at every tool call, and a switch mid-reply is told to the model with the next tool result (`MODE_SWITCHED`); `setMode` is how the overlay's "Do it for me" switches the reply to do (the chat's mode chip goes through `Chat.setComputerMode`, which also hands over a step that waits); `stop` is the chat's Stop for that reply. `decideMode(text, previous)` reads a message for doing it or showing how (`intent.ts`, no model call); `previous` is what the chat's last message was read as, which follow-ups like "next" keep. Put `modeTag(mode, text)` in front of each user message. A "just do it" typed during a Show-me step (`handsOver`) switches the running reply to do. `effortFor(model)` gives Tomo's effort. The module's `end` releases its waits, and after the last computer reply turns content protection off and lets the Stop shortcut go.
- **Steps**: the module's own tools send steps with `tool: 'computer_<name>'`. While one runs, `computer.onDoing` reports it live (quiet looks too, as "Looking at the screen"); the chat shows it in the step list and drops it once the finished step has landed. Live lines are never saved. Claude Code runs the built-ins (Read, Glob, Grep, WebSearch, Bash) itself; the module's `stepFor` (`builtinStep`) gives their lines, which the driver adds when each call's result comes back.
- **Stop**: the chat's Stop runs `computer.stop` as well as stopping the reply. Input stays off until `computer.userTurn`, which `module` runs. The overlay port holds the global Stop shortcut (`STOP_SHORTCUT` in `@shared/computer`) while a computer reply runs; pressing it runs `stop` and every running reply's `stop`.
- **Waits**: `computer.subscribe` reports the approval or Show-me step waiting on the user (with its `sessionId` and `messageId`), and `null` when none is. The chat answers with `computer.approve(id, approved)` and `computer.teachDone(id)`. A message the user types during a Show-me step goes to `teachDone(id, teachAnswer(text))`: "done" and the like finish the step, anything else is passed on. The overlay's presses carry the wait's id: Done, Can't find it and Do it for me on the callout, and Approve (armed after `APPROVE_ARM_MS`, as in the chat) and Deny in the notch, which asks a waiting approval. A click step (`CLICK_STEP`) also ends when the user clicks inside the spotlight: on Windows the host's `pressed` reads the button state every 100 ms (no hook), and the step counts as done 600 ms later. macOS and Linux have no cheap read (each would start a process), so there only the buttons end it. While a step waits, its spotlight re-reads the control's rect every second (by element id, or what is at the middle of a snapped control) and follows it.

## Behaviour

- The overlay (`overlay.ts`) is one full-screen, click-through window: the acting frame, the Show-me spotlight and its callout (draggable, kept where dragged until the next step 1), and the notch, shown while a computer reply runs and no chat-v2 window has focus. It takes the mouse only while the pointer is on the callout or the notch: main polls the pointer every 40 ms against the rects the page reports. Electron's `forward` option isn't used, because on Windows it is a low-level mouse hook that Windows drops when the main thread stalls. The window is focusable, because Chromium drops a click on a window that can't be activated (`MA_NOACTIVATEANDEAT`). After a press or a drag, `refocus` gives focus back to the app under it.
- The notch wraps a MacBook's camera housing. Electron doesn't report the housing, so `cameraHousing` reads it from the built-in screen: a menu bar of 30 pt or more, or a screen narrower than 1.58:1.
- Screenshots are 1024 px wide. Coordinates in screenshot pixels map to the monitor of the window being worked in. The pointer is drawn in on Windows (the host) and macOS (`screencapture -C`).
- Acting tools (click, type_text, press_keys, scroll, drag, move_mouse) wait `SETTLE_MS` (400 ms) and answer with a fresh full screenshot, which becomes the coordinate frame, plus whether the active window changed and, after clicks, typing and keys, the focused control (Windows). `screenshot: false` skips it.
- `look_at_screen` with `region` (a rect in the last full screenshot's pixels) captures that part of the screen at up to its own resolution (at most 1024x768). A zoom never becomes the coordinate frame; its text says how its pixels map back, so a pixel click is never ambiguous.
- ui_elements lines carry state where the platform reports it: `value="…"` (fields, combo boxes, sliders, documents; never password fields), checked / unchecked / mixed, selected, expanded / collapsed, disabled. Windows reads them from UI Automation patterns in the same cached call; macOS from AX value, enabled and selected. Its `window` option reads another window by title or app name without focusing it (Windows and macOS).
- Clicks take `double`, `triple` and `modifiers` (held for the click and always released); `move_mouse` hovers.
- A reply is stopped after 80 acting calls, or 240 reads (looks, control and window lists, searches, waits), which only guard against a loop.
- Before each input, focus goes back to the app the user was in. On Windows, when a chat-v2 window is in front, that app is the topmost app window under it in z-order. On macOS it is the app of the frontmost normal window that isn't chat-v2's.
- If the mouse moves more than 28 px from where computer use left it, the reply pauses.
- Windows only: a window running as administrator drops chat-v2's input, so the tools say so instead of trying.
- Linux (`platform/linux.ts`) needs an X11 display (not Wayland or XWayland) and the command-line tools `xdotool`, `xprop`, `wmctrl`, ImageMagick's `import`, `find`, `grep` and `xdg-open` (Debian: `xdotool x11-utils wmctrl imagemagick xdg-utils`); a missing tool is reported as such. The tools always run with a UTF-8 locale.
  - It can't read controls yet (`controls: false`), so ui_elements isn't offered and the Linux prompt tells the model to work from screenshots and pixels.
  - Linux can't hide windows from capture, so when chat-v2 is in front a screenshot first brings the remembered app back. The overlay isn't shown on Linux (without a compositor X11 draws it solid black over the screen); set `CHAT_V2_LINUX_OVERLAY=1` to show it on a desktop with a compositor.
  - Focus: restoreFocus falls back to the next app window if the remembered one closed, skips panels, docks and desktop windows, and fails if the app won't come to the front, so input never lands in chat-v2.
  - Typing: ASCII goes in short `xdotool type` chunks so Stop never cuts a key press in half. Non-ASCII characters are sent as Unicode key presses, capitals with Shift, because `xdotool type` lowercases capital non-ASCII letters.
  - Keys: names and punctuation are mapped to X keysyms (`ctrl+/` → `ctrl+slash`), and a key xdotool doesn't know is an error, not a silent no-op.
  - `open` takes a path, a URL, or an app by its name or command name, never a command line: arguments would run without the approval shell commands need.
- **Point** (`point.ts`, `pointing.ts`, the overlay's `PointLayer.svelte`): the user marks a spot, a control or a box on screen for their next message, from the composer's Point button (shown while computer use is on in the chat), Ctrl+P (Cmd+P), or Point in the notch. The overlay covers the display under the pointer (and follows it to another display, except mid-drag) and takes every click; Esc, a right-click or Cancel ends it. Started from the chat, the chat windows are minimised meanwhile and come back after. Hovering highlights the control under the pointer where the platform has `pointAt` (Windows: the host's hit test, which looks past chat-v2's own windows, since the overlay covers the point). The finished mark becomes two attachments: a PNG of the area around it with the mark drawn in (captured with `desktopCapturer` after the overlay hides), and `point-<time>.md`, which gives the mark in the pixels of a look_at_screen screenshot of that display (`frameFor`: the monitor scaled to 1024 px wide on Windows, the main display on macOS, the whole X screen on Linux), the control and window under it, and screen coordinates. Removing either chip removes both. macOS and Linux have no `pointAt`, so the note has no control or window there; Linux needs `CHAT_V2_LINUX_OVERLAY=1` for Point at all. While Point is on, a running computer reply's input stops as a takeover (it would land on Point's layer; a typing run stops at its next chunk), and presses don't count as a click inside a Show-me spotlight, nor for 400 ms after (the click that finished the mark).
- Every chat-v2 window has content protection while a computer reply runs, so none appears in screenshots. That also hides them from screen sharing for that time.

## Design

Everything computer use draws, in the chat and on the overlay, is one family. Its tokens and shared pieces are in `src/renderer/src/computer/computer.css`, which both the chat (`app.css`) and the overlay page (`computer/main.ts`) load.

- **Palette.** Near-monochrome. In the chat, the app's own tokens (`--fg`, `--bg`, `--line`, `--hover`), so it follows the theme. On the overlay, floating parts sit on `.cu-ink`: a warm near-black (`--cu-ink`) with paper text (`--cu-paper`) in both themes, so they read on any wallpaper; an inner 1px hairline keeps the edge on dark wallpapers and a low, wide shadow (`--cu-float`) lifts it off light ones. No glows and no `backdrop-filter` (it is unreliable on a transparent window).
- **Accent.** The ember appears only where it means "the agent is acting": the acting frame around the screen and the breathing status dot (`.cu-dot`). Waiting on the user is a steady ring in the text colour. Point's mark is ember too, as it is drawn into the image that goes with the message.
- **Type.** The app's faces: Instrument Sans for UI, JetBrains Mono for keys, counts and exact targets. Sizes: 11–11.5 px meta (counts, tags), 12.5 px UI and buttons, 15–16 px at weight 450–500 for the one thing to read (an instruction, an approval's title). Counts use tabular figures.
- **Shapes.** Pills for every button and chip (`.cu-btn`: 28 px, or 24 px `.small`). Primary is solid ink in the chat and solid paper on ink (`.primary`); secondary is a hairline pill (`.line`); the ways out are quiet pills that show a wash on hover. Keys are small mono chips with a hairline (`.cu-kbd`, grouped in `.cu-keys`). Cards have a 16 px radius, inner blocks 10 px.
- **Arming.** Approve's pill fills from the left over `APPROVE_ARM_MS` (`.arming` + `.cu-fill`), then takes clicks. The primary pill's background eases only into hover, so the end of arming can't flash.
- **Motion.** Calm and short: enter 200–280 ms (fade, a 6 px rise, or a slide from the screen edge for the notch), exit 160–200 ms, glides 420 ms, all on `--cu-ease`. The only loop is the status dot's slow breathing; the Show-me spotlight pings once per step instead of pulsing. Every Svelte transition here and every CSS animation honours `prefers-reduced-motion`.
- **No flicker.** Nothing that is the same thing re-mounts: the notch is one element that opens downwards into the approval panel (grid rows 0fr → 1fr) and folds back, and a Show-me step moves the same callout and spotlight. A part main turns off stays 160 ms more on the overlay (`HOLD`), so a state that flaps (the chat window taking focus for a moment, a step ending just as the next starts) doesn't blink. Widths don't follow text: the notch is 380 px in every state, the step line's chevron is always laid out, and the mode chip sits at the far end of its line. In the chat, a step line that changes faster than 180 ms waits out the dwell, a live tool's line gives way to its finished step without showing both, and the finished count rolls into the same slot. When the reply ends, the Stop hint's row folds away with its gap (`collapse` in `lib/motion.ts`), so nothing below it jumps. A finished Point says it was added through its chips and the composer taking focus, with no toast over the composer.
- **Hit areas.** Whenever anything on the overlay moves (a glide, the notch opening, a part leaving), the page reports its `data-hit` rects every frame until it settles, and parts on their way out (inert) take no clicks, so the area main uses never lags what is drawn.

## Packaging

The Windows host (`host.ps1` and `host.cs`) is inlined in `platform/hostSource.ts`, so it ships inside app.asar. On first use it is written to `%LOCALAPPDATA%\chat-v2\computer-host\<hash>\`, and host.ps1 compiles the C# once into a DLL beside it. The first start takes about 1.5 s, later ones about 0.8 s.

## Tests

- `bun test test/computer`: Control, the tools and the policy against a fake platform, and the real Windows host with read-only calls only.
- `DISPLAY=:99 bun test test/computer/linux.test.ts`: the Linux parsers, and with an X display, window manager and xterm, the real Linux platform: windows, focus, screenshots, clicks, typing, Stop and file search. Without a display only the parsers run.
- `bun run build && bun test/computer/render-overlay.ts [dir]`: renders the acting frame, a Show-me step, the notch (also around a MacBook camera) and Point (a hovered control, a box) to PNGs without showing a window.
- `bun run build && bun test/computer/render-states.ts [dir] [scale]`: close-ups of every overlay state in both themes on a light, a dark and a busy wallpaper, and frame sequences across changes (the notch opening for an approval and closing, its text changing, a focus flap, a step moving on or leaving, the frame flapping) with the drawn and reported hit rects per frame in `sequences.json`. `REDUCED=1` emulates reduced motion.
- `node test/computer/render-chat.mjs <playwright-core dir> <dir> [light|dark] [scale]`, after `bun run build`: the chat's parts (Computer switch and Point, live step line, Stop hint and mode chip, failed and denied steps, the approval and Show-me cards, Point's chips) as close-ups, and sequences of a paced run, the approval arming and leaving and a Show-me step moving on, with a scripted model (`polish-query.ts`) and a fake platform (`polish-platform.ts`). `CV2_REPO` points it at another checkout's build, to compare before and after.
- `bun test test/computer/pointing.test.ts`: Point's coordinates (against Control's own mapping), crop, mark and note.
- `bun test/computer/live-look.ts ["request"]`: one look-only reply with the real SDK (Haiku, teach mode). It uses the Claude Code login.
- `bun test test/chat.test.ts -t "computer use"`: computer replies through the chat, with a fake `query` and platform.
- `node test/computer/e2e.mjs <playwright-core dir> [out dir]`, after `bun run build`: the hidden app with a scripted model and a fake platform (`CHAT_V2_FAKE_COMPUTER`). It clicks Approve and Deny (in the chat and in the notch), Show-me Done, Can't find it and Do it for me, the mode chip, a click inside a moving spotlight, drags the callout, checks the live step line, uses the notch and its Stop, and Stop, and captures the cards. Then Point: hover, Esc, a second start, a click on a control and a box, with the fake platform's `pointAt` and `capture`; the note reaches the scripted model. With a stand-in pointer it checks the overlay takes the mouse only over its controls.
